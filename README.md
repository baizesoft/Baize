# 白泽编程语言（Baize）

> **让所有中国人都能够使用中文编程。**
>
> 让编程回归中文，让创造没有语言障碍。

白泽是一门为中文原生设计的通用编程语言。它不只是把现有语言的关键字翻译成中文，而是希望从语言语法、类型系统、标准库、错误诊断、开发工具到教学文档，都以中文作为第一语言体验。

项目长期目标是建设一门兼具简洁表达、原生并发、系统性能、企业级工程能力、科学计算能力和跨平台能力的中文编程语言，并最终实现以汇编种子启动、由白泽自身完成编译器和工具链自举的自主工具链。

- 源文件扩展名：`.bz`
- 源码编码：UTF-8
- 当前阶段：编译器自举原型，正在从 C 代码发射路线向原生机器码工具链规划演进
- 项目优先级：P2（长期核心技术资产，持续积累；不挤占 P0/P1 客户交付资源）
- 当前研发分支：`dev`
- 稳定基线分支：`main`

## 愿景与设计目标

白泽研究并吸收成熟语言的优秀设计思想，但不拼接它们的语法，也不以模仿某一门语言为最终目标。

| 设计方向 | 研究对象 | 白泽目标 |
|---|---|---|
| 原生并发 | Go | 轻量任务、结构化并发、消息通信、调度与异步 I/O |
| 简洁表达 | Python | 语法清晰、表达自然、减少样板代码，适合初学者 |
| 企业级工程 | Java | 强类型、模块化、稳定兼容、可维护性与工具链 |
| 系统性能 | C | 低开销、可控资源、原生机器码和系统接口能力 |
| 跨平台 | Go / Rust 等 | Windows、Linux、macOS，以及 x86-64、ARM64 等目标架构 |
| 科学计算 | 数值计算生态 | 数组、向量化、矩阵、线性代数、并行与 GPU 扩展 |

### 中文原生原则

1. 中文是语言的原生设计语言，而不是外围翻译层。
2. 关键字、标准库 API、编译错误、工具提示、教程和官方文档以中文为第一体验。
3. 语法设计以可读、明确、一致为先，不机械翻译 Go、Python、Java 或 C。
4. 对数字、运算符、硬件接口、文件格式和外部 ABI，允许遵循通用技术约定；这不改变中文作为语言主体的原则。
5. 中文标识符、Unicode、源代码位置和错误诊断必须作为语言核心能力长期验证。

## 自主工具链与自举原则

白泽最终目标是：**编译器、运行时、标准库和核心工具链由白泽自身掌握；最终编译器不依赖 Rust、Go、Python、C 等第三方高级编程语言作为实现基础。**

这是一项分阶段目标，不代表当前已经实现。

建议的自举路线：

1. **Stage 0：汇编种子。** 为每个初始目标架构建立尽可能小、可审计的汇编种子编译器。早期可以使用现有汇编器/链接器完成种子构建，但必须记录可信根和外部工具依赖。
2. **Stage 1：白泽编译器。** 使用 Stage 0 编译以白泽编写的编译器源码，逐步直接生成目标机器码或目标文件。
3. **Stage 2：白泽编译白泽。** 使用 Stage 1 编译同一份编译器源码，验证编译器能够自我构建。
4. **Stage 3：可重复自举。** 连续多代编译器对相同源码生成可解释、可比较的产物，并建立独立构建、哈希比对和信任链验证。

严格说明：

- 自举不可能脱离一切初始可信根。Stage 0 的汇编源码仍需要某种方式转换为机器码；初期可借助现有汇编器/链接器，但它们属于明确记录的过渡依赖。
- “不依赖第三方高级编程语言”与“最终不依赖任何外部工具链”是两个不同里程碑。后者还需要逐步建设白泽自己的汇编、目标文件/可执行文件生成、链接能力和构建工具。
- 汇编种子通常与指令集和 ABI 相关。跨平台需要按目标架构维护种子或建立可信的交叉构建链，不能假设一份汇编程序天然适用于所有平台。
- Rust/C 可以作为当前原型和迁移阶段的研究工具，但不得被误称为最终自主工具链。

## 当前实现（dev 分支）

当前代码已经超过初始化阶段，具备 Windows/MSVC 上的编译器自举原型：

- Rust 种子编译器位于 `src/`，Cargo 包名为 `baize-seed`。
- 白泽编译器源码位于 `compiler/编译器.bz`。
- 白泽编译器已实现词法扫描、递归下降语法分析、AST 构造和 C 代码发射。
- Rust 种子可生成 Stage 1；随后可禁用种子可执行文件，由 Stage 1 生成 Stage 2、Stage 2 生成 Stage 3。
- 当前验证脚本会比较连续阶段生成的 C 源码哈希，并运行中文程序、字符串、运算、递归、数组、文件读写、命令行参数及错误输入等样例。

当前原型支持范围与限制：

- 中文关键字和标识符、UTF-8 字符串。
- 数字、布尔值、一元负号、算术和比较表达式。
- 函数、参数、递归、整型变量、赋值、条件、循环、返回和输出。
- 固定大小字节数组及索引读写。
- 目前生成 C，后续仍依赖 C 工具链。
- 数组边界检查、完整类型系统、模块/包系统、错误诊断、跨平台行为和运行时能力仍需持续完善。
- 当前公开验证重点是 Windows/MSVC；不能据此宣称 Linux、macOS、ARM64 已通过。

当前 Windows 验证入口：

```powershell
powershell -ExecutionPolicy Bypass -File scripts/build-seed.ps1
powershell -ExecutionPolicy Bypass -File scripts/verify-seed.ps1
powershell -ExecutionPolicy Bypass -File scripts/verify-bootstrap.ps1
```

运行环境需要 Rust/Cargo、Visual Studio 2022 MSVC 和 Windows SDK。以上是当前原型的过渡性依赖，不代表最终目标。

## 长期技术路线

1. **语言定义：** 语言宪章、语法规范、类型系统、泛型、模块、错误处理和兼容性政策。
2. **编译器核心：** 词法、语法、AST、类型检查、中间表示、优化、诊断和调试信息。
3. **原生后端：** 先选择明确的目标架构，研究机器码、目标文件、ABI、链接和可执行文件格式。
4. **汇编种子与自举：** 建立 Stage 0，逐步减少并最终消除高级语言实现依赖。
5. **运行时与内存：** 内存安全策略、资源生命周期、并发调度、异步 I/O 和系统接口。
6. **标准库：** 文件、网络、时间、数据库、加密、数学、集合和跨平台抽象。
7. **并发与云原生：** 轻量任务、Channel、结构化并发、服务开发、网络协议和容器环境。
8. **科学计算：** 数组、向量化、矩阵、线性代数、并行计算及可选 GPU 能力。
9. **开发者生态：** 包管理、构建、测试、格式化、静态分析、调试器、IDE/LSP 和中文教程。
10. **跨平台：** Windows、Linux、macOS；x86-64、ARM64，按明确的宿主/目标矩阵逐步验收。

## 项目原则

- 先研究、定义契约和验收标准，再进行大规模编码。
- 优先借鉴成熟编译器理论与实现；每项依赖都审查许可证、安全、维护状态和可替代性。
- 过渡实现与最终架构明确区分，记录每项外部依赖及退出计划。
- 以真实可运行程序、测试、可重复构建和自举证据衡量进度，不以语法示例或愿景文案宣称完成。
- 保持项目长期 P2 定位；客户交付和经营关键任务优先。
- 重要架构决策、语言规范和阶段成果写入白泽知识库，并由空明独立审查。
